# 문서 규약

작성자가 코드를 읽지 않으므로 문서가 유일한 검토 지점이다. 그래서 문서에 빠진 절이 있으면 설계에 빠진 판단이 있다는 뜻이다. 이 문서는 그 빠짐을 눈에 보이게 한다.

## 왜 이 규약이 필요했나

첫 설계 문서가 이렇게 나왔다.

| 증상 | 원인 |
|---|---|
| `DOMAIN.md` 에 정의가 없고 제외 목록만 있었다 | 선행 PoC 의 상수를 목록으로 옮겼다. 옮기는 작업에는 «왜» 를 묻는 단계가 없다 |
| 명사가 데이터만 담고 동사는 따로 있었다 | PoC 의 `track` 객체와 `trackFix()` 함수 구조를 계층 이름만 바꿔 옮겼다 |
| 패턴 목록에 대안과 기각 근거가 없었다 | 확인 가능한 것(상수·게이트)으로 채우고 판단이 필요한 곳을 비웠다 |
| 한 파일에 설명·참조·절차가 섞였다 | 문서 종류를 나눈다는 개념 자체가 없었다 |

넷 다 **형식이 없어서** 빠진 것이 보이지 않은 결과다. ADR 은 형식이 있어서 104줄을 47줄로 줄일 수 있었다.

## 문서 종류를 섞지 않는다

[Diátaxis](https://diataxis.fr/) 의 네 종류를 쓴다. 한 파일에 두 종류를 담지 않는다.

| 종류 | 독자가 원하는 것 | 이 레포의 문서 |
|---|---|---|
| 설명 | 왜 이렇게 됐는지에 대한 서술 | `ARCHITECTURE.md`, `adr/` |
| 참조 | 값과 규칙의 완전한 목록 | `DOMAIN.md` |
| 사용법 | 목적을 이루는 절차 | `VERIFICATION.md` |
| 학습 | 처음 오는 사람의 경로 | `README.md` |

섞이면 독자가 무엇이 하중을 받는 부분인지 구분할 수 없다.

## 문서별 필수 절

빠진 절이 있으면 미완성이다. 분량이 아니라 빠짐으로 판정한다.

### `DOMAIN.md` (참조)

| 절 | 없으면 |
|---|---|
| 도메인 정의 (한 문장) | 새 기능이 안인지 밖인지 판단할 기준이 없다 |
| 하위 도메인 구분 (핵심·지원·일반·다른 컨텍스트) | 모든 기능이 같은 모델로 들어와 진흙 공이 된다 |
| 유비쿼터스 언어 | 문서와 코드와 대화가 다른 낱말을 쓴다 |
| 값 객체와 규칙 | 단위 혼용 사고가 다시 난다 |
| 집합체마다 **갖는 행위**와 **불변식** | 빈혈 모델이 된다 |
| 정책 판정식과 상수 | 구현이 맞는지 확인할 기준이 없다 |

프레임워크 이름이 한 번도 나오지 않아야 한다. 나오면 아키텍처 문서로 갈 내용이다.

### `ARCHITECTURE.md` (설명)

[C4 model](https://c4model.com/) 의 층을 쓴다. 한 그림에 두 축척을 담지 않는다.

그림은 `docs/diagrams/` 에 SVG 로 두고 그림과 표를 함께 둔다. 그림은 관계를 한눈에 보여주고 표는 검색되며 세부를 담는다. 생성 도구에 라벨 배치를 맡기면 겹쳐서 읽을 수 없게 된다. 직접 배치한다.

**고치기 전에 그려서 본다.** `node tools/render-diagrams.mjs` 가 SVG 를 이미지로 만든다. 좌표를 보지 않고 적으면 라벨이 겹치고, 겹친 것을 사람이 발견할 때까지 모른다. 실제로 세 번 그렇게 됐다. 상자가 스무 개를 넘어 손 배치가 버거워지면 도구로 넘긴다.

**용어는 독자가 쓰는 말로 적는다.** 분야 은어를 끌어오지 않는다. 실제로 `측위`·`발화`·`타일` 을 썼다가 전부 바꿨다. 유비쿼터스 언어는 팀이 실제로 쓰는 말이어야 한다.

| 절 | 없으면 |
|---|---|
| 도메인 한 줄 (`DOMAIN.md` 참조) | 아키텍처가 무엇을 담는지 모르고 읽는다 |
| 1층 시스템 맥락 | 외부 의존이 무엇인지, 어느 것이 되돌리기 어려운지 모른다 |
| 2층 컨테이너 (따로 배포되는 단위) | **몇 개를 배포하는지 드러나지 않는다.** 같은 로직이 여러 컨테이너에 중복돼도 보이지 않는다 |
| 3층 컴포넌트 (계층·의존 방향·포트) | 교체 지점과 의존 규칙을 모른다 |
| 4층 코드 | 그리지 않는다. `DOMAIN.md` 가 대신한다 |
| 패턴마다 **막는 문제 · 대안 · 기각 근거** | 목록만 남고 판단이 사라진다 |
| 기계 강제 장치 | 사람이 검토하지 않는데 아무도 검토하지 않는 상태가 된다 |

2층이 빠져서 실제로 문제가 생겼다. 계층 그림은 컨테이너 한 개 안의 이야기라서 컨테이너 수가 나오지 않고, 그래서 웹과 앱이 같은 도메인을 각자 구현하는 상태가 문서에 보이지 않았다.

절차와 측정은 여기 두지 않는다.

### `adr/NNNN-*.md` (설명)

[adr/README.md](adr/README.md) 를 따른다. Nygard 다섯 절. 분량은 상한이 아니라 점검 신호로 둔다.

## 도메인을 정의하는 절차

명사부터 시작하면 데이터베이스 표가 나온다. 동사부터 시작한다.

| 순서 | 하는 일 |
|---|---|
| 1 | 일어나는 일을 **과거형 동사**로 나열한다 (도메인 사건) |
| 2 | 그 동사들을 한 문장으로 압축한다. 그것이 정의다 |
| 3 | 정의 밖의 개념을 지원·일반·다른 컨텍스트로 가른다 |
| 4 | 아래 기준으로 정의의 폭을 확인한다 |
| 5 | 동사를 책임지는 명사를 세우고 불변식을 부여한다 |

**정의의 폭 판정**

| 상황 | 판정 |
|---|---|
| 새 기능에 정의를 고쳐야 한다 | 너무 좁다. 핵심을 잘못 잡았다 |
| 정의를 고치지 않고 하위 도메인으로 붙는다 | 맞다 |
| 정의가 새 기능을 막지도 허락하지도 않는다 | 너무 넓다. 경계 구실을 못 한다 |

**빈혈 판정**

명사가 행위를 갖지 않고 별 함수가 그 명사를 조작하면 빈혈이다. 판정 질문은 하나다. **불변식을 누가 지키는가.** 밖에서 지키면 지키지 않는 경로가 반드시 생긴다.

## 작업 단위

| 상황 | 이슈와 PR |
|---|---|
| 기능 변경 | 이슈 하나에 PR 하나 |
| 초기 설계 형성 | 문서들이 서로를 고치며 같이 만들어진다. **하나로 합친다** |
| 검증·교정 누락 | 별 작업이 아니다. 원 변경의 PR 에 포함한다 |

미완성을 새 이슈로 잘라내지 않는다. 앞 PR 이 열려 있는 동안 같은 파일을 건드리는 다음 작업을 시작하지 않는다.
