# 확인 절차

이 문서는 **어떻게 확인하는가**를 담는다. 무엇이 맞아야 하는지는 [DOMAIN.md](DOMAIN.md), 왜 그렇게 설계했는지는 [ARCHITECTURE.md](ARCHITECTURE.md) 에 있다.

## 확인을 네 층으로 나눈다

이 앱은 손으로 시험하기 어렵다. 선행 검증에서 결함 하나 확인에 20분이 들었고, 그래서 결함이 몰려서 뒤늦게 드러났다.

| 층 | 무엇을 보나 | 명령 | 사람 손 | 시간 |
|---|---|---|---|---|
| 0 | **배경 위치 수신 + 화면 꺼진 상태의 소리** | `npm run test:device` | 기기 잠금 해제 (같은 와이파이면 케이블 불필요) | 2분 |
| 1 | 거리·페이스·구간 템포·도달 판정·결손 처리 | `npm test` | 없음 | 즉시 |
| 2 | 조작·음성·저장·요약·상태 전이 | `npm test` | 없음 | 즉시 |
| 3 | GPS 정확도·도플러 속도 품질·배터리 | 실측 | 30분 러닝 | 30분+ |

1·2층은 게이트에서 커버리지로도 잰다. 도메인·애플리케이션 층 라인 80% 미만이면 게이트가 실패한다. 화면·어댑터는 측정 범위 밖이다. 각자의 확인 층(그림·기기 시험)이 따로 있다. 실측 수치는 `~/git-project/idean3885/coverage-ledger.md` 에 쌓는다.

값이 맞는지는 시험이 보지만 **화면이 어떻게 보이는지는 보는 수밖에 없다.** 그래서 층을 하나 더 둔다.

| 명령 | 하는 일 | 판정 |
|---|---|---|
| `npm run test:screen` | 시뮬레이터를 띄워 위치를 흘려 넣고 그림을 남긴다 | 사람이 그림을 본다 |

그림 여섯 장이 나온다. 각 장이 만드는 상태가 다르다.

| 그림 | 만드는 상태 | 보는 것 |
|---|---|---|
| `1-ready` | 코스 없이 처음 실행 | 빈 공간이 남는가 · 버튼이 살아 있는가 |
| `2-running` | 지점 둘을 심고 표식으로 달리기 시작 | 시간이 흐르는가 · 페이스가 사람 범위인가 · 경로와 지점이 그려지는가 |
| `3-suggest` | 보관함을 심고 시작 자리를 코스 시작점에 맞춘다 | 추천 카드가 코스 이름과 지점 수를 적는가 |
| `4-courses` | 표식으로 코스 화면을 연다 | 칸 수가 보이는가 · 지우는 길이 있는가 |
| `5-records` | 기록 둘(경로 있는 것·없는 것)을 심고 표식으로 기록 화면을 연다 | 날짜·거리·시간·평균 페이스가 적히는가 |
| `6-blocked` | 위치 접근을 거두어 지하와 같은 결과를 만든다 | 배너가 맨 위에 있는가 · 달리기가 잠겼는가 |

화면을 누를 방법이 호스트에 없다. 그래서 눌러야 열리는 화면은 표식 파일로 연다. 표식은 앱이 읽는 즉시 지운다.

이 층이 없어서 결함 셋을 놓쳤다. 종료 뒤에도 시간이 흘렀고, 제자리에서 페이스가 폭주했고, 화면 3분의 2가 비어 있었다. **시험 62개와 기기 시험 둘이 모두 통과한 상태였다.** 값의 정확함과 화면의 온전함은 다른 사실이다.

0 층은 두 경로를 각각 확인한다. 진단만 자동화하면 확인된 것은 진단이고 제품은 아니다.

| 명령 | 경로 | 판정 |
|---|---|---|
| `npm run test:device:diag` | 진단 화면 | 배경 위치 수신 · 음성이 끝까지 재생 |
| `npm run test:device:run` | 달리기 화면 | 달리기가 배경에서 위치를 받는가 |

둘 다 표식 파일을 넣어 앱이 스스로 시작하므로 시작 버튼을 누르지 않는다.

**진단 화면을 사람이 여는 길은 없다.** 표식 파일이 있을 때만 열린다. 사람이 보는 화면은 달리기 하나이고, 진단이 남긴 것은 기기에서 가져온 `trace.jsonl` 을 읽어서 본다. 화면으로 볼 때는 눈이 판정 도구인데 기록으로 보면 세는 것이 판정이므로, 같은 것을 두 방식으로 판정하지 않는다.

0 층을 사람이 걷는 일로 두지 않는다. 제자리에서도 확인되고, 확인되지 않는 것은 기기 볼륨과 무음 스위치 둘뿐이다. 실측은 3 층 하나로 모은다.

### 0 단계를 맨 앞에 두는 이유

위험 순서와 편의 순서가 다르다. 편의로 보면 모킹으로 기능을 다 만들고 마지막에 실측하는 것이 빠르다. 그런데 **아직 확인되지 않은 최대 위험**이 그 마지막에 숨는다.

선행 검증으로 확인한 것은 **웹**의 백그라운드 불가다. 네이티브에서 되는 것은 거의 확실하지만 확인된 것은 아니다. 권한 흐름, 백그라운드 작업 등록, 제조사 배터리 관리가 각각 걸릴 수 있다. 만든 것을 다 쌓고 마지막에 막히면 쌓은 것 전부가 걸린다.

그래서 첫 조각을 **위치 어댑터 하나와 진단 화면 하나**로 둔다. 도메인도 달리기 화면도 없이 수신 건수만 센다. 소리도 같이 본다. 화면이 꺼진 상태에서 음성이 실제로 들리는지는 같은 조건에서 확인되므로 함께 본다.

버릴 코드로 두지 않는다. 위험을 없애는 것은 코드를 버리는 것이 아니라 **첫 조각을 얇게 두는 것**이다. 어댑터는 통과하면 그대로 쓰고, 진단 화면은 실측에서 문제가 날 때마다 다시 필요하다. 근거는 [ADR 0006](adr/0006-diagnostic-screen-over-throwaway-spike.md).

### 1 층과 2 층은 한 구현을 공유한다

위치 포트에 재생 어댑터를 주입하면 CI 단위 시험과 기기 모의 달리기가 같은 장치로 해결된다. 근거는 [ADR 0004](adr/0004-replay-adapter.md).

### 모킹이 못 보는 것

초록불을 "됩니다" 로 읽지 않기 위해 적어둔다.

| | 대역으로 보이는 것 | 기기에서만 보이는 것 |
|---|---|---|
| 음성 | 올바른 시점에 올바른 문구로 불렀는가 | 배경에서 끝까지 재생되는가 |
| 위치 | 어댑터가 값을 옳게 옮겼는가 | 배경에서 계속 오는가 |

불렀다는 것과 들렸다는 것은 다른 사실이다. 선행 검증에서 정확히 이 틈에 빠졌다. 오디오가 "재생 중" 으로 보이는데 실제로는 꺼져 있었다.

**0단계에서 이 틈이 다시 나왔고, 이번에는 기기 시험이 잡았다.** 음성 결과 콜백을 기록에 남기자 배경에서는 재생이 시작만 되고 끝나지 않는 상태였다. 그래서 판정을 "불렀다"가 아니라 "끝까지 재생됐다"로 둔다. 소프트웨어가 볼 수 없는 것은 기기 볼륨과 무음 스위치 둘로 좁혀진다.
