# 확인 절차

이 문서는 **어떻게 확인하는가**를 담는다. 무엇이 맞아야 하는지는 [DOMAIN.md](DOMAIN.md), 왜 그렇게 설계했는지는 [ARCHITECTURE.md](ARCHITECTURE.md) 에 있다.

## 확인을 네 층으로 나눈다

이 앱은 손으로 시험하기 어렵다. 선행 검증에서 결함 하나 확인에 20분이 들었고, 그래서 결함이 몰려서 뒤늦게 드러났다.

| 층 | 무엇을 보나 | 실외 | 비용 |
|---|---|---|---|
| 0 | **백그라운드 위치 수신 + 화면 꺼진 상태의 소리** | 5분 산책 | 반나절 |
| 1 | 거리·페이스·구간 템포·도달 판정·결손 처리 | 없음 | 0 |
| 2 | 조작·알림·음성·저장·요약·상태 전이 | 없음 | 분 단위 |
| 3 | GPS 정확도·도플러 속도 품질·배터리 | 30분 러닝 | 30분+ |

### 0 단계를 맨 앞에 두는 이유

위험 순서와 편의 순서가 다르다. 편의로 보면 모킹으로 기능을 다 만들고 마지막에 실측하는 것이 빠르다. 그런데 **아직 확인되지 않은 최대 위험**이 그 마지막에 숨는다.

선행 검증으로 확인한 것은 **웹**의 백그라운드 불가다. 네이티브에서 되는 것은 거의 확실하지만 확인된 것은 아니다. 권한 흐름, 백그라운드 작업 등록, 제조사 배터리 관리가 각각 걸릴 수 있다. 만든 것을 다 쌓고 마지막에 막히면 쌓은 것 전부가 걸린다.

그래서 첫 조각을 **위치 어댑터 하나와 진단 화면 하나**로 둔다. 도메인도 주행 화면도 없이 수신 건수만 센다. 소리도 같이 본다. 화면이 꺼진 상태에서 음성이 실제로 들리는지는 같은 조건에서 확인되므로 함께 본다.

버릴 코드로 두지 않는다. 위험을 없애는 것은 코드를 버리는 것이 아니라 **첫 조각을 얇게 두는 것**이다. 어댑터는 통과하면 그대로 쓰고, 진단 화면은 실측에서 문제가 날 때마다 다시 필요하다. 근거는 [ADR 0006](adr/0006-diagnostic-screen-over-throwaway-spike.md).

### 1 층과 2 층은 한 구현을 공유한다

위치 포트에 재생 어댑터를 주입하면 CI 단위 시험과 기기 모의 주행이 같은 장치로 해결된다. 근거는 [ADR 0004](adr/0004-replay-adapter.md).

### 모킹이 못 보는 것

초록불을 "됩니다" 로 읽지 않기 위해 적어둔다.

| | 모킹으로 보이는 것 | 기기에서만 보이는 것 |
|---|---|---|
| 음성 | 올바른 시점에 올바른 문구로 호출됐는가 | 화면 꺼진 상태에서 실제로 들리는가 |
| 알림 | 발행 요청이 갔는가 | 잠금화면에 떴는가, 소리·진동이 났는가 |
| 위치 | 어댑터가 값을 옳게 옮겼는가 | 백그라운드에서 계속 오는가 |

호출됐다는 것과 들렸다는 것은 다른 사실이다. 선행 검증에서 정확히 이 틈에 빠졌다. 오디오가 "재생 중" 으로 보이는데 실제로는 꺼져 있었다.
