# 작업 도구 측정

## 왜 측정하나

이슈 플로우·검증·콘텐츠 도구를 통합한 개인 하네스([claude-ops-agent](https://github.com/idean3885/claude-ops-agent))를 만들어 두고, 실제 프로젝트에 처음부터 끝까지 걸어본 적이 없다. 이 프로젝트가 첫 대상이다.

목적은 점수를 내는 게 아니라 **어디가 비었는지 찾는 것**이다. 측정이 작업보다 비싸지면 그건 측정 실패다. 그래서 마일스톤마다 한 번, 표 한 줄씩만 남긴다.

## 무엇을 쓰나

| 도구 | 이 프로젝트에서 쓰는 자리 |
|---|---|
| `flow` | 모든 변경. 이슈 → 명세 → 구현 → 커밋 → PR |
| `advisor` | 설계 문서를 성장 방향 렌즈로 비판 |
| `cross-verify` | 되돌리기 어려운 결정 앞에서 정합 확인 |
| `learn` | 어긋난 지점을 규칙으로 승격 |
| `content-write` → `verify` → `publish` | 배운 것을 글로 |
| 표현 가드 hook | 문서 작성 중 상시 |

조직 전용 도구 계층은 이 프로젝트에 닿는 면이 좁다. 그것도 결과이므로 별도로 기록하되, 이 레포에는 남기지 않는다. 개인·조직 자원을 다루는 계층이라 제품 문서와 표면이 다르다.

## 지표

| 지표 | 세는 방법 | 무엇을 뜻하나 |
|---|---|---|
| 플로우 우회 | 이슈 없이 들어간 커밋 수 | 0 이 아니면 플로우가 쓰기 불편한 자리가 있다 |
| 분기 이슈 | 도구의 빈 자리를 발견해 만든 이슈 수 | 많을수록 하네스에 빠진 것이 많았다 |
| advisor 반영률 | 지적 중 실제 수정으로 이어진 비율 | 낮으면 렌즈가 이 프로젝트에 안 맞는다 |
| cross-verify 전복 | 검증으로 뒤집힌 결정 수 | 0 이면 검증이 형식이었을 수 있다 |
| 표현 가드 통지 | 위반 통지 횟수 | 줄어들지 않으면 룰이 실제 습관을 교정하지 못한다 |
| 문서만으로 재개 | 세션 재개 때 코드를 읽어야 했는가 | 읽어야 했다면 문서가 계약 구실을 못 한다 |

## 언제 적나

**마일스톤에 닿을 때 한 줄.** 마일스톤은 사람이 기기에서 확인할 수 있는 상태에 도달한 시점이다. PR 마다 적으면 이 표가 변경 이력이 되고, 그러면 지표가 아니라 기록 부담이 된다.

한 줄이 빠진 채로 다음 마일스톤에 가지 않는다. 실제로 이슈 다섯 건이 기록 없이 지나갔고, 원인은 적을 시점이 이 문서 안에 없었던 것이다. 규칙은 [CLAUDE.md](../CLAUDE.md) 에도 있다.

미측정은 미측정으로 적는다. 부르지 않은 도구를 0 으로 적으면 「썼는데 아무 일도 없었다」로 읽히고, 그것이 이 표가 답해야 하는 물음을 망친다.

2026-08-15 의 결함 둘은 같은 원인이다. **가드를 넣을 때 새로 막으려던 상태만 시험했고 이미 되던 상태를 지나가지 않았다.** 그리고 버튼 눌림 판단이 화면 안에 있어 시험이 볼 수 없었다. 판단을 세션으로 올리고 생애주기 상태 10개를 표로 고정했으며, 판단이 화면으로 돌아가지 못하게 소스 관문을 뒀다. 그 관문이 작업 중 실제로 어시스턴트 코드를 한 번 잡았다.

기록이 판정 도구로 처음 값을 냈다. 기기 화면을 볼 수 없는 상태에서 「10초마다 같은 실패」와 「권한 응답 + 시작 조건 통과」를 구분한 것이 `trace.jsonl` 이었다.

2026-08-14 의 전복이 미측정인 이유는 검증을 부르지 않았기 때문이다. 되돌리기 어려운 결정이 둘 있었다. 코스 보관함을 코스와 따로 두는 설계와, 도메인 구현 두 벌 상태를 끊는 결정. **둘 다 교차 검증 없이 갔다.** 0 이 아니라 미측정으로 적는 이유가 이것이다. 부르지 않은 도구를 0 으로 적으면 검증이 형식이었다는 뜻으로 읽힌다.

같은 날 기록이 빠진 사실도 지표다. 이슈 다섯 건이 지나가는 동안 이 표에 아무것도 적히지 않았고, 사람이 물어서 드러났다. 적을 시점이 문서에 없으면 빠진다.

분기 이슈 1건은 `advisor` 프로파일을 두는 유저 스코프 디렉토리를 만드는 주체가 없어 첫 조회가 실패하는 문제였다 ([#252](https://github.com/idean3885/claude-ops-agent/issues/252)).

2026-08-21 의 「문서만으로 재개」가 아니오인 이유는 화면 페이스 표시 정책이 계약에 없었기 때문이다. 메인 계기판이 어떤 페이스를 보여주는지 문서 어디에도 없어 구현을 읽어야 했고, 그 자리에서 결함(기록 달리기에 구간이 안 생김)이 나왔다. 계약이 비어 있으면 코드가 계약이 되고, 그러면 결함이 사양처럼 보인다. 그 정책을 [ADR 0011](adr/0011-splits-close-on-passage-average-pace-main.md) 로 계약에 넣었다.

전복 1건은 캐패시터 전환안이다. 시험 자산이 생겼다는 이유로 채택 방향까지 갔다가, 정본 문서에서 배경 위치 지원 여부를 확인하고 기각했다 ([ADR 0005](adr/0005-capacitor-reconsidered.md)). **검증 없이 결정을 말한 것이 원인이고, 검증이 그것을 잡았다.** 검증 절차가 형식이 아니었다는 첫 사례다.

달리기 화면의 전복 1건은 도메인 규칙이다. 지도에서 지점을 찍으려면 기준 경로가 필요한데 첫 달리기 전에는 없어서, 편의를 위해 「경로가 없으면 어디든 허용」으로 바꿨다. 그 뒤 `DOMAIN.md` 에 반대 규칙이 이미 있는 것을 발견하고 코드를 문서에 맞춰 되돌렸다. **문서가 코드를 되돌린 첫 사례다.**

"문서만으로 재개" 가 예인 근거도 여기에 있다. 구현 중에 문서를 근거로 판단이 뒤집혔다는 것은 문서가 계약 구실을 했다는 뜻이다.

2026-08-13 의 전복 1건은 음성 판정이다. 배경에서 음성이 "나갔다"고 본 상태였는데, 결과 콜백을 기록에 남기자 배경 구간에서는 재생이 시작만 되고 끝나지 않는다는 것이 드러났다. 웹에서 빠졌던 틈과 같은 자리다. 원인은 `AVSpeechSynthesizer` 가 기본으로 앱의 오디오 세션을 쓰는데 그 세션을 활성화한 적이 없었던 것이고, 시스템 관리 세션으로 돌려 해결했다.

"문서만으로 재개" 가 이 줄에서 예로 바뀐 이유는 설계 문서가 정리된 뒤 코드를 읽지 않고 다음 작업을 이어갈 수 있었기 때문이다. 아래 문단은 그 전 상태의 기록이다.

"문서만으로 재개" 가 아니오인 이유는 세션이 끊긴 뒤 프로토타입 코드를 다시 읽어야 했다는 것이 아니라, 프로토타입 자체가 문서 계약 밖에 있어서 비교 대상이 없었다는 뜻이다. 앱 구현이 시작되면 이 칸의 뜻이 제대로 선다.

## 판정

프로젝트가 끝날 때 두 물음에 답한다.

1. **1인 토이 프로젝트에서 이 하네스가 쓸 만한가.** 플로우 우회가 잦았다면 규칙이 무겁다는 뜻이다
2. **문서를 계약으로 두고 코드를 읽지 않는 방식이 성립하는가.** 코드를 읽어야 했던 횟수가 답이다

두 답이 다 "아니다" 라도 결과다. 그때는 무엇을 덜어낼지가 정해진다.
