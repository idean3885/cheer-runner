# ADR 0003. 코드 검토를 기계 장치로 대체한다

- 상태: 채택
- 날짜: 2026-08-12
- 관련: `docs/ARCHITECTURE.md`, `docs/MEASURE.md`, ops-agent `docs/design-philosophy.md` 결정 2

## 배경

작성자는 이 프로젝트의 코드를 읽지 않는다. 설계와 도메인을 배우는 것이 목적이고, 구현은 위임한다.

그러면 사람이 코드를 읽어 잡던 것들이 아무도 잡지 않는 상태가 된다. 계층 위반, 타입 우회, 다역 함수, 조용히 삼킨 오류가 그것이다. PoC 에서 실제로 다 났다.

동시에 AI 는 매번 같게 동작하지 않는다. 어제 합의한 계층 규칙을 오늘 어긴다. 문서에 적어두는 것만으로는 다음 세션에 지켜지지 않는다.

## 결정

**규칙을 문서에 적는 것에서 멈추지 않고 CI 에서 실패하게 만든다.** 문서는 왜 그런지를 담고, 장치는 어긋남을 막는다.

| 규칙 | 문서 | 장치 |
|---|---|---|
| 도메인은 프레임워크를 모른다 | `ARCHITECTURE.md` 계층 표 | `dependency-cruiser` 규칙 |
| 단위를 숫자로 두지 않는다 | `DOMAIN.md` 값 객체 | TypeScript `strict`, `no-explicit-any` |
| 함수는 한 가지만 한다 | `ARCHITECTURE.md` 스멜 표 | eslint `complexity` 10, `max-lines-per-function` 40 |
| 오류를 삼키지 않는다 | 같음 | eslint `no-empty` |
| 정책은 시험된다 | `DOMAIN.md` 정책 | `domain` 커버리지 하한 90% |
| 변경에는 이력이 있다 | — | ops-agent `flow` (이슈 → PR) |

ops-agent 의 설계 사상을 그대로 가져온 것이다. 사람이 기억하는 규칙은 잊히고, 문서에만 있는 규칙은 안 읽히고, 하네스에 있는 규칙은 매번 걸린다.

## 기각한 대안

**AI 에게 자기 코드를 검토하게 한다.** 같은 세션의 같은 모델이 방금 쓴 코드를 검토하면 자기 전제를 그대로 승인한다. 별 세션·별 관점으로 돌리면 나아지지만, 그건 결정론적 장치가 아니라 확률적 도구다. 보조로는 쓰되 관문으로는 쓰지 않는다.

**작성자가 최소한만 읽는다.** "핵심만 본다" 는 실행되지 않는다. 어디가 핵심인지 판단하려면 이미 읽어야 한다. 전제를 흐리지 않고 아예 읽지 않는 쪽으로 굳힌다.

**장치를 나중에 붙인다.** 코드가 쌓인 뒤 계층 규칙을 걸면 위반이 한꺼번에 나오고, 그때는 규칙을 느슨하게 고치는 쪽으로 기운다. 파일이 몇 개일 때 걸어야 규칙이 이긴다.

## 받아들이는 대가

**초기 구성 비용.** 코드 한 줄 전에 설정 파일이 여럿 생긴다. 토이 앱에 과하다는 느낌이 들 지점이다.

**장치가 못 잡는 것이 남는다.** 계층을 지키고 타입이 맞고 시험이 통과하면서도 도메인이 틀릴 수 있다. 페이스 공식이 잘못돼 있는데 그 잘못된 공식으로 시험을 짜면 초록불이 켜진다. 이건 장치로 막을 수 없고 `DOMAIN.md` 의 계약이 맞는지로만 막힌다. 그래서 그 문서가 개념 소개가 아니라 판정식과 상수를 적은 계약 형태여야 한다.

## 결과

- 첫 이슈에 설정 파일과 CI 를 포함한다. 기능 코드보다 먼저 들어간다
- 작성자의 검토 지점은 셋으로 고정한다 — `docs/` 문서, CI 결과, 실기기 동작
- 문서와 구현이 어긋났는데 CI 가 통과하는 사례가 나오면, 규칙을 느슨하게 하지 않고 장치를 추가한다. 그 사례를 `MEASURE.md` 에 기록한다
