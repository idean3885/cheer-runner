# ADR 0004. 재생 어댑터 하나로 CI 시험과 기기 모의 주행을 함께 덮는다

- 상태: 채택
- 날짜: 2026-08-12
- 관련: `docs/MVP.md` 확인 4층, `docs/ARCHITECTURE.md` 포트, [ADR 0002](0002-domain-as-pure-fold.md)

## 배경

ADR 0002 가 도메인을 순수 접기 연산으로 두면서 계산 정확성은 CI 에서 확인할 수 있게 됐다. 그런데 확인해야 할 것이 계산만은 아니다.

- 화면이 올바른 값을 보여주는가
- 도달할 때 알림이 발행되고 음성 문구가 맞는가
- 코스가 저장되고 다시 불러와 시작되는가
- 상태 전이가 규칙대로만 일어나는가

이것들은 도메인 밖이라 순수 시험으로 덮이지 않는다. 선행 검증에서는 이 확인을 실제 주행으로 했고 한 번에 20분씩 들었다.

## 결정

**위치 포트에 재생 어댑터를 하나 두고, 그것을 시험 대역과 기기 모의 주행에 함께 쓴다.**

```
ReplayLocationAdapter ─┐
                       ├─> LocationPort ─> 유스케이스 ─> 화면·알림·음성·저장
ExpoLocationAdapter ───┘
```

지도와 화면은 포트 **위**에 있으므로 위치가 어디서 왔는지 모른다. 어댑터만 갈아끼우면 그 위 전부가 가짜 측위로 돈다.

재생 어댑터를 개발용 토글로 앱에 넣어두면 **같은 바이너리로** CI 단위 시험과 기기 모의 주행이 된다. 확인 4층 중 1층과 2층이 한 구현을 공유한다.

## 재생 어댑터의 요건

**플랫폼이 주는 모양 그대로 넣는다.** 도메인 값 객체를 바로 넣으면 운영 어댑터의 매핑이 시험되지 않고, 단위를 잘못 읽거나 필드를 잘못 옮긴 버그가 모든 시험을 통과해 실측에서만 드러난다.

**배속을 둔다.** 시각은 고정 표본에서 오고 도메인은 벽시계를 읽지 않으므로 배속이 계산 결과를 바꾸지 않는다.

| 배속 | 쓰는 자리 |
|---|---|
| 즉시 | CI. 20분 주행이 밀리초에 끝난다 |
| 5~10배 | 기기 모의 주행. 기능·화면·저장 확인 |
| 1배 | 응원 문구와 시점의 느낌 확인 |

배속을 올리면 음성 안내가 몰려 들리므로 느낌은 1배로만 본다.

**표본은 합성으로 시작한다.** 일정 속도, 급감속, 15초 결손, 정확도 200m 잡음, 652초 단절을 각각 만든다. 경계 조건은 합성이 실측보다 정확하게 만들 수 있다. 실측 표본은 회귀 가치가 있으므로 앱이 기록을 낼 수 있게 되면 추가한다.

## 확인 순서를 뒤집는다

모킹이 좋은 도구인 것과, 모킹이 실전 확인을 미루는 핑계가 되는 것은 다르다.

| | 편의 순서 | 채택한 순서 |
|---|---|---|
| 먼저 | 모킹으로 기능 전부 | 백그라운드 위치·소리 하나만 |
| 나중 | 실측 | 나머지 전부 |

선행 검증으로 확인한 것은 **웹**의 백그라운드 불가다. 네이티브에서 되는 것은 거의 확실하지만 확인된 것은 아니다. 권한 흐름, 백그라운드 작업 등록, 제조사 배터리 관리가 각각 걸릴 수 있다.

만든 것을 다 쌓고 마지막에 막히면 쌓은 것 전부가 걸린다. 그래서 **버릴 코드**로 위치만 받는 최소 앱을 먼저 만들어 5분 산책으로 찍는다. 반나절이면 끝나고, 통과한 뒤에 본 설계로 간다.

## 기각한 대안

**화면 시험 중심 (Testing Library).** 화면이 깨졌는지만 알려준다. 이 앱에서 틀리면 아픈 것은 거리·페이스·구간 템포이고 그건 화면 밖에 있다. 안 짜는 게 아니라 우선순위를 뒤에 둔다.

**실기기 자동화 (Detox·Maestro).** 백그라운드 위치 거동은 결국 실기기로 봐야 하므로 언젠가 필요하다. 다만 그건 통합 확인이고, 기능 정확성을 여기에 맡기면 왕복이 다시 분 단위로 돌아간다.

**수신 간격을 촘촘히 해 정확도를 올린다.** 표본 수와 오차는 다르다. 초당 1회로 올리면 표본은 늘지만 각 측위의 오차 반경은 그대로다. 좌표 차이를 합하는 방식에서는 잡음이 지그재그로 쌓여 **거리가 과대 측정된다**. 정확도는 필터로 올린다 — 도플러 속도 우선, 정확도 컷, 속도 상한. 그리고 촘촘한 요구는 배터리를 먹고 백그라운드에서 더 적극적으로 조절되므로, 지금 최우선인 백그라운드 지속과 상충한다. 수신 간격은 백그라운드 생존에 맞춰 잡고, 간격을 좁히는 것은 필터를 다 넣고도 부족할 때 마지막에 쓴다.

## 받아들이는 대가

**개발용 토글이 운영 빌드에 남을 위험.** 재생 어댑터를 앱에 넣으므로 실수로 켜진 채 배포될 수 있다. 빌드 설정으로 운영에서는 조립 지점에서 제외한다.

**모킹이 덮지 못하는 범위가 남는다.** 음성은 "올바른 시점에 올바른 문구로 호출됐는가" 까지만 보이고 "화면 꺼진 상태에서 실제로 들리는가" 는 보이지 않는다. 알림도 같다. 그 경계를 [MVP.md](../MVP.md) 에 표로 적어 초록불을 "됩니다" 로 읽지 않게 한다.

## 결과

- 위치 포트 구현체는 둘. 조립 지점에서 개발 토글로 고른다
- 재생 어댑터의 입력 타입은 플랫폼 모양이며, 도메인 값 객체 직접 주입은 `dependency-cruiser` 로 막는다
- `toFix` 를 순수 함수로 떼어내 CI 에서 시험한다
- 0 단계(백그라운드 위치·소리 확인)를 첫 작업으로 둔다. 그 결과 없이 본 설계 구현을 시작하지 않는다
