# 기획 의도와 첫 릴리스 범위

## 의도

```
1. 달리기 시작
2. 특정 지점 도달 시 화면을 터치해 현재 위치를 목표로 지정
3. 그렇게 N개 지정 → 순서 기록
4. 달리기 완료
5. 다음 달리기에서 그 코스를 뛰면, 목표 지점 도달 시 응원 음성
```

기본기는 셋이다. **GPS, 페이스 측정, 목표 사이 템포.**

## 달리기에 두 종류가 있다

| | 기록 달리기 | 따라가기 달리기 |
|---|---|---|
| 언제 | 코스를 처음 달릴 때 | 그 코스를 다시 달릴 때 |
| 사용자가 하는 일 | 힘든 자리에서 화면을 터치 | 달리기만 한다 |
| 앱이 하는 일 | 그 순간의 위치를 지점으로 기록 | 지점 도달을 알리고 응원 |
| 남는 것 | 순서가 있는 지점 목록 | 구간별 템포 기록 |

배타가 아니다. 기존 코스를 달리다 지점을 하나 더 찍는 경우가 있으므로 한 달리기 안에서 겹칠 수 있다.

## 구간은 내가 의미를 준 지점으로 나뉜다

다른 러닝 앱은 100m·1km·시간처럼 균일한 단위로 구간을 끊는다. 그 단위에는 뜻이 없다. 이 앱은 **내가 힘들었던 자리로** 끊는다. "3구간이 8분 10초" 가 아니라 "그 언덕 구간이 8분 10초" 가 된다.

"목표 사이 템포" 를 기본기로 둔 것이 이 뜻이다.

## 응원이 보상이다

점수도 배지도 아니다. 힘든 자리에 닿았을 때 앱이 그걸 알고 있다는 것 자체가 보상이다. 그 자리는 사용자가 직접 표시한 곳이므로 앱은 언제 응원해야 하는지 안다.

## 지점을 만드는 세 경로

지점을 만드는 방법이 셋이고, 갈리는 기준은 **사용자가 이미 무엇을 알고 있어야 하는가** 다.

| | 경로 | 언제 | 알고 있어야 하는 것 | 필요한 화면 |
|---|---|---|---|---|
| A | 달리며 터치 | 달리기 중 | 없음. 지금 힘들면 누른다 | 큰 버튼 하나 |
| B | 내 트랙에 사후 추가 | 달리기 직후 | 방금의 기억 | 내 트랙만 그린 지도 |
| C | 지도에서 사전 지정 | 아무 때 | 그 지역 지리 | 자유 지도, 검색, 주소 |

### 여기서 기능이 갈린다

요구 지식만이 아니라 성격이 다르다.

- **A·B 는 지나간 자리에 표시한다.** 내가 실제로 그 좌표를 통과했으므로, 같은 코스를 다시 달리면 반경 안에 반드시 든다
- **C 는 가보지 않은 자리에 예약한다.** 지도에서 찍은 점을 실제 경로가 안 지날 수 있고, 그러면 응원이 오지 않는다. 사용자는 앱이 고장났다고 본다

이 차이가 기능을 나누는 근거다. C 를 넣을 때는 **"이 지점은 아직 지나간 적이 없습니다"** 표시가 함께 가야 한다. 그게 없으면 C 는 조용히 실패하는 기능이 된다.

### B 의 설계 요점

핀을 **트랙 위로 붙인다.** 탭은 2차원으로 받고 가장 가까운 트랙 점으로 스냅해 1차원 선택으로 만든다. 임의 좌표를 허용하면 그 순간 B 가 C 가 되고 C 의 위험까지 따라온다.

그래서 B 의 지도는 C 의 지도보다 가볍다. 역할이 다르다. C 는 지도가 **탐색** 도구지만 B 는 **확인** 도구다. 내 트랙만 보이면 되고 검색·주소·다른 장소가 필요 없다.

첫 릴리스의 B 는 지도 없이 낸다. B 의 본질은 트랙 위 한 점 고르기이고 그건 1차원 선택이므로, 종료 요약 화면에 트랙을 100m 간격으로 목록화하고 항목을 눌러 지점으로 올린다.

```
2.1km · 12분 30초 · 페이스 5'57"   [지점으로]
2.2km · 13분 05초 · 페이스 5'50"   [지점으로]
```

방금 달린 직후라면 "그 언덕이 2km 쯤" 이 붙는다. 개발 검증에는 충분하고, 지인에게 넘길 때 지도로 승격한다.

## 첫 릴리스에 있는 것

| 기능 | 내용 |
|---|---|
| 달리기 시작·종료 | 버튼 하나로 토글. 시작은 사용자 행위로만 |
| 위치 추적 | 백그라운드 포함. 화면을 끄고 달릴 수 있어야 한다 |
| 거리·시간·페이스 | 현재 페이스와 전체 페이스 |
| 지점 지정 (A) | 달리는 중 화면 터치 → 현재 위치를 지점으로 |
| 지점 지정 (B) | 종료 요약에서 트랙 목록 항목을 지점으로 승격 |
| 코스 저장 | 지점 목록에 이름을 붙여 저장 |
| 코스 선택 | 저장된 코스 목록에서 골라 시작 |
| 도달 응원 | 지점 반경 안에 들면 음성으로 응원 |
| 구간 템포 | 지점 사이 거리·시간·페이스. 도달할 때 읽어준다 |
| 종료 요약 | 전체 거리·시간·페이스, 구간 목록, 트랙 목록 |
| 모의 달리기 | 개발용 토글. 기록된 트랙을 실제 경로로 흘려 넣는다 |

## 첫 릴리스에 없는 것

미루는 것이지 버리는 것이 아니다. 순서를 정한 이유를 함께 적는다.

지도 화면과 경로 그리기는 미루려 했으나 먼저 들어왔다. 지점을 어디에 찍었는지 목록으로는 확인할 수 없었고, 두 번째 달리기에서 응원이 맞는 자리에서 오는지 보려면 지점이 지도 위에 있어야 했다. B(사후 승격) 는 그래서 지도로 대체돼 목록 형태로 만들지 않았다.

| 미루는 것 | 왜 |
|---|---|
| 지점 지정 (C) | 도달 보장이 없어 성격이 다르다. 별 기능으로 가른다 |
| 피버·점수 | 응원이 먼저 통하는지 봐야 한다. 안 통하면 점수를 추가해도 안 통한다 |
| 강아지·배지 | 점수 위에 서는 것이므로 점수 뒤 |
| 지점 삭제·순서 편집 | 첫 릴리스에서는 코스를 다시 만드는 게 더 빠르다 |
| 달리기 기록 목록 | 종료 요약만 있으면 한 번은 돌아본다 |
| 보고서 전송 | 개발 계측이다. 필요해지면 그때 |

## 확인 절차

확인을 네 층으로 나눈다. 0 단계를 통과하기 전에는 달리기 화면을 만들지 않는다.
절차와 각 층의 내용은 [VERIFICATION.md](VERIFICATION.md) 에 있다.

## 익스팬드 전략: 웹을 남겼고, 조건이 차서 걷었다

앱을 만드는 동안 웹 프로토타입을 확인 도구로 유지했다. 웹은 배경 위치만 못 하고 나머지 로직은 다 돌았다.

| 시기 | 웹 | 앱 |
|---|---|---|
| 앱 개발 중 | 유일한 확인 수단. 자동 시험이 여기서 돌았다 | 개발 |
| 앱이 0 단계를 통과한 뒤 | 로직 확인용으로 유지 | 실기기 확인 |
| 앱 쪽 시험이 같은 판정을 낸 뒤 | 걷었다 | 주 사용 |

**정리 시점을 «앱이 안정된 뒤» 가 아니라 «앱 쪽 시험이 같은 표본으로 같은 판정을 낼 때» 로 뒀다.** 자동 시험이 웹 페이지를 대상으로 돌았기 때문에, 웹을 먼저 지우면 시험도 같이 지우는 상태였다. 그리고 도메인 규칙이 두 곳에 구현된 상태를 오래 두면 한쪽만 고치는 실수가 난다.

조건으로 판정한 결과가 이렇다. 웹 시험 9건 중 7건은 앱 시험이 같은 판정을 내고, 남은 2건은 웹에서만 성립하는 물음이다. 판정 대조와 남긴 것은 [ARCHITECTURE.md](ARCHITECTURE.md) 의 2층에 적었다.

정리 직전 상태에서 이미 한쪽만 고쳐지고 있었다. 앱에만 있던 것이 코스 보관함, 시작 조건 가드, 알림음, 이탈 판정, 페이스 표본 하한이었다. **실수가 사고로 보이지 않은 이유는 아무도 웹을 고치지 않았기 때문이고, 그것은 정리 시점이 지났다는 신호였다.**

## 다음 릴리스를 여는 조건

첫 릴리스로 확인할 것은 하나다. **같은 코스를 두 번째 달릴 때, 지점에서 오는 응원이 실제로 도움이 되는가.**

되면 지도와 트랙을 추가해 코스를 눈으로 보게 하고, 그다음 피버와 점수를 추가한다. 안 되면 응원 방식을 먼저 고친다. 문구, 시점, 음성 대 진동 중 어디가 문제인지 본다. 점수로 덮지 않는다.
