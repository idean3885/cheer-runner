# 치어러너 (cheer-runner)

달리다 힘든 자리에서 화면을 한 번 누른다. 다음에 그 코스를 달리면 **그 자리에서 응원이 온다.**

다른 러닝 앱은 100m·1km·시간처럼 균일한 단위로 구간을 끊는다. 그 단위에는 뜻이 없다. 치어러너는 **내가 힘들었던 자리로** 끊는다. "3구간 8분 10초" 가 아니라 "그 언덕 8분 10초" 가 된다.

## 상태

실기기에서 달리기가 돈다. 배경 위치 수신과 화면 꺼진 상태의 소리를 확인했고(0단계), 거리·페이스·구간 템포·지점 도달 응원이 동작한다. 코스는 기기에 저장되고 시작 자리 근처면 불러오기를 권한다.

아직 확인하지 않은 것이 하나 남았다. **같은 코스를 두 번째 달릴 때 지점에서 오는 응원이 실제로 도움이 되는가.** 그것이 첫 릴리스로 확인할 유일한 물음이다.

선행 검증에서 순수 웹으로 만들어 확인한 결과, **iOS 웹은 백그라운드에서 위치를 받지 못한다**는 것이 측정으로 확정됐다. 근거는 [ADR 0001](docs/adr/0001-cross-platform-choice.md). 그래서 Expo 기반 React Native 로 다시 만들었다.

그 웹 프로토타입은 앱 시험이 같은 표본으로 같은 판정을 낸 뒤 걷었다. 측정값은 코드가 아니라 `DOMAIN.md` 와 `ARCHITECTURE.md` 에 글로 남아 있다.

## 왜 응원인가

혼자 달리면 그만두기 쉽다. 그래서 힘든 자리를 **사용자가 직접 표시한다.** 그 자리는 사용자가 고른 곳이므로 앱은 언제 응원해야 하는지 안다.

점수도 배지도 아니다. 힘든 자리에 닿았을 때 앱이 그걸 알고 있다는 것 자체가 보상이다.

## 표기

층마다 형태가 다르다. 하이픈이 허용되는 자리와 안 되는 자리가 갈린다.

| 층 | 값 | 비고 |
|---|---|---|
| 홈 화면 | 치어러너 | 4자라 줄임표로 잘리지 않는다 |
| 레포 | `idean3885/cheer-runner` | 케밥 케이스 |
| 도메인 | `cheer-runner.idean.me` | 하이픈은 라벨 안에서 쓸 수 있다. 맨 앞·맨 뒤만 안 된다 |
| 번들 ID · 패키지명 | `me.idean.cheerrunner` | 안드로이드 패키지명이 하이픈을 막는다. 그래서 붙여 쓴다 |
| 딥링크 scheme | `cheerrunner` | 번들 ID 와 같은 형태 |

번들 ID 하나만 되돌리기 어렵다. 스토어에 올린 뒤에는 바꿀 수 없다. 바꾸면 다른 앱이 된다.

## 만드는 방식

작성자는 코드를 읽지 않는다. 설계와 도메인 모델링을 익히는 것이 목적이고 구현은 위임한다. 그래서 사람이 코드를 읽어 검출하던 것을 기계가 검출한다. 계층 규칙, 구문·경로 해석, 함수 크기, 도메인 시험이 CI 관문이고 전체가 2초 안에 끝난다. 근거는 [ADR 0003](docs/adr/0003-machine-gates-replace-code-review.md).

검토 지점은 셋이다. 문서, CI 결과, 실기기 동작.

## 확인 비용

이 앱은 손으로 시험하기 어렵다. 좌표를 옮기려면 이동해야 하고, 백그라운드를 보려면 화면을 끄고 달려야 한다. 그래서 확인을 네 층으로 나눈다.

| 층 | 무엇을 보나 | 실외 |
|---|---|---|
| 1. 도메인 리플레이 | 거리·페이스·구간 템포·도달 판정·결손 처리 | 없음 |
| 2. 기기 모의 달리기 | 조작·소리·음성·저장·요약·상태 전이 | 없음 |
| 3. 화면 확인 | 시뮬레이터에 위치를 흘려 넣어 그림을 남긴다. 사람이 본다 | 없음 |
| 4. 산책 확인 | 백그라운드 위치 수신, 화면 꺼진 상태의 소리 | 5분 |
| 5. 실측 러닝 | GPS 품질·배터리 | 30분 |

1층과 2층은 같은 구현을 공유한다. 위치 포트에 재생 어댑터를 주입하면 CI 단위 시험과 기기 모의 달리기가 한 장치로 해결된다. 근거는 [ADR 0002](docs/adr/0002-domain-as-pure-fold.md).
